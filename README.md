# PowerMill AI — ассистент по Autodesk PowerMill (локально)

RAG-ассистент для технологов ЧПУ: отвечает по **оффлайн-справке PowerMill**,
генерирует PML-макросы, считает режимы резания, разбирает ошибки.
Работает полностью офлайн: Ollama + ChromaDB + SQLite FTS5.

Это **Уровень 1** из плана: «GitHub Copilot для PowerMill» — подсказывает,
генерирует куски кода, объясняет ошибки.

## Где лежит документация (главное открытие)

Справка Autodesk PowerMill собрана генератором «wrapped HTML», и в папке
`files\` **нет текста** — только заглушки:

```
C:\ProgramData\Autodesk\PowerMill\2026\Help\l.rus\
├── files\           1350 × *.htm   по ~850 БАЙТ — ПУСТЫШКИ (только скрипты!)
├── wrapped-files\   1350 × *.htm.js  0.5–55 КБ — ЗДЕСЬ НАСТОЯЩИЙ ТЕКСТ страниц
├── contexthelp\     1255 × *.htm   термины-указатели (страницы-редиректы)
└── scripts\
    ├── toc-treedata.js     дерево оглавления со всеми заголовками
    └── search-entries*.js  поисковый индекс Autodesk (позиции слов)
```

Именно поэтому «парсинг HTML» по `files\*.htm` давал **0 страниц**: 850 байт —
это `document.write(...)`, а сам текст лежит в `wrapped-files\<имя>.htm.js`
внутри JS-строки (с экранированием `\"`, `\u0413`, склейками `"a" + "b"`).

Что делает проект (см. `src/help_extract.py` и `src/html_parser.py`):

1. находит языковую папку (`l.rus`, `l.enu`, …) — без дублей RU+EN;
2. берёт текст из `files\*.htm`, а если там заглушка — разворачивает
   `wrapped-files\*.js` (все варианты обёрток: `document.write`, `append`,
   `innerHTML`, конкатенация, `\uXXXX`-escape);
3. подтягивает **заголовок и иерархию** из `scripts\toc-treedata.js`
   (например, `Начало работы > Введение > Установка домашней папки`);
4. чистит навигацию/«было полезно?», сохраняет структуру: `## Заголовки`,
   `- списки`, `| таблицы |`, `[рисунок: …]`;
5. читает метаданные Autodesk (`contextid`, `topic-type`, `topicid`) — по ним
   находится страница, если технолог спрашивает служебным именем диалога;
6. привязывает термины из `contexthelp\` к настоящим статьям как «также: …»
   (сначала по ссылке редиректа, затем по совпадению `contextid`) — термины
   из подсказок начинают находить нужный раздел;
   6а. читает **справочник PML** из установки PowerMill
   (`E:\powermill 2026\PowerMill 2026\lib\locale\C`: папки `PARREF`, `PARSUM`,
   `DOC`, `HELP`, включая `.txt`/`.xml`) — описания параметров и команд PML;
7. режет **гигантские страницы** (справочник параметров PML: `toolpath.html` —
   575 000 символов) на части по заголовкам, иначе одна таблица вытесняла из
   поиска статьи руководства;
8. присваивает источникам приоритет: руководство (`files\`) → термины
   (`contexthelp\`) → справочник параметров (`PARREF`) — теперь на «swarf»
   первым идёт статья руководства, а не таблица параметров;
9. пишет `output\help_pages.jsonl`, `output\help_toc.txt`, `output\help_report.txt`,
   а ход работы — в `output\logs\parse_help.log` (лог нужен, если окно закрылось).

## Как работает поиск

Гибрид, слияние по Reciprocal Rank Fusion (`src/retrieval.py`):

| Канал | Что ловит | Где |
|---|---|---|
| Вектора (ChromaDB + MiniLM-multilingual) | смысл, перефразировку | `src/vectorstore.py` |
| Ключевые слова (SQLite **FTS5**, встроен в Python) | точные термины: `Thickness`, `HOLDER_CLEARANCE`, «D16», русскую морфологию через усечение окончаний | `src/help_search.py` |

Строгие FTS-совпадения считаются релевантными всегда, векторные — только при
`distance ≤ SOURCE_MAX_DISTANCE`. Если векторная база пуста, ассистент всё
равно отвечает по FTS (и наоборот). Смена модели эмбеддингов требует полной
пересборки: `python -m src.vectorstore`.

### Если Inventor-файл (.ipt) не импортируется в PowerMill

Ошибка «**Inventor Interoperability Engine is currently unavailable. Try again**»
(встречается как Error 81 / Ошибка 0) — известная проблема Autodesk, а не твоя
ошибка: импорт `.ipt` делает отдельный компонент **Inventor Interoperability**,
который НЕ ставится вместе с PowerMill.

Лечение (по официальной статье Autodesk):

1. зайди в свою учётную запись Autodesk: `manage.autodesk.com`;
2. **Product Updates** (Обновления продуктов);
3. скачай и поставь **Inventor Interoperability** нужной версии (для PowerMill
   2026 — 2026);
4. после установки `.ipt` открывается и в PowerMill, и в Manufacturing Data
   Exchange Utility.

Пока компонента нет — обычный рабочий путь: **Inventor → Сохранить как → STEP
(.stp)**, затем импорт STEP в PowerMill. Для механообработки это даже лучше:
STEP передаёт точные поверхности, а `.ipt` при конвертации разбивается на
треугольники (`sdxOptWriteTrianglesToSecondaryFile:true` в логе конвертера),
и PowerMill дольше считает траектории по такому «сетчатому» телу.

### Два «мозга»: локальная модель и облачный API

Справка в обоих случаях одна и та же — выдержки подбираются поиском (RAG) и
уходят модели вместе с вопросом. Меняется только тот, кто их читает.

| | Локальная Ollama | Облачный API |
|---|---|---|
| Стоимость | бесплатно | ~1–15 ₽ за сотню вопросов (зависит от сервиса) |
| Интернет | не нужен | нужен |
| Железо | грузит ПК (RTX 3060, 16 ГБ RAM) | не грузит |
| Качество PML/таблиц | слабое: путает регистр, выдумывает команды | заметно точнее |
| Приватность | всё остаётся на компьютере | выдержки по вопросу уходят на сервер |

Как подключить (2 минуты):

```
start_menu.bat  ->  пункт 21   (выбрать сервис, вставить ключ, проверить связь)
start_menu.bat  ->  пункт 22   (переключиться на API или обратно на Ollama)
start_menu.bat  ->  пункт 7    (проверка: покажет, отвечает ли ИИ)
```

Готовые варианты в `setup_api.bat`: OpenAI, OpenRouter (один ключ на много
моделей), DeepSeek (дешёвый и сильный в коде), Groq (есть бесплатный лимит),
свой адрес (любой OpenAI-совместимый сервис, включая Ollama на
`http://localhost:11434/v1`).

Ключ сохраняется в `E:\powermill-ai\api_key.json` — **вне репозитория**,
в Git не попадает (`.gitignore` его тоже закрывает). Ошибки объясняются
по-русски: неверный ключ (401) → «запусти пункт 21», лимит (429) → «подожди
минуту», нет сети → «проверь интернет».

Ориентир по выбору модели: для PML и таблиц бери модель не меньше 70B
(`deepseek-chat`, `llama-3.3-70b-versatile`, `gpt-4o-mini`) — тогда макросы
перестают выдумывать команды. Проверка `src\pml_vocab.py` всё равно работает:
даже умная модель иногда ошибается, а она покажет конкретные строки.

### Генерация макросов: почему ей можно верить

Модель охотно пишет «красивый» PML, которого не существует. Например, на задачу
«создать границы по всем отверстиям модели» выдавался макрос с такими строками:

```pml
Create Boundary "Silhouette" $e     // неверный регистр + лишний аргумент
Add Default Allowance $e           // таких команд в PML нет
Check Toolpath $e                  // и таких тоже
```

Поэтому в проекте есть три опоры:

| Что | Зачем |
|---|---|
| `output\pml_vocabulary.txt` / `.json` | словарь настоящих имён: типы объектов (`boundary`, `toolpath`, `tool`, `model`…) и имена параметров (`Thickness`, `SwarfBasePosition`…), собранный из разобранной документации |
| `src\pml_vocab.py` | проверяет готовый макрос: неизвестные типы объектов, несуществующие команды, регистр (PML его различает), лишние аргументы у `CREATE`. В чате показываются конкретные строки-подозреваемые, а в `.mac`-файл пишется шапка с номерами этих строк |
| `data\macros` (и найденное пунктом 20) | настоящие рабочие макросы становятся статьями базы знаний: `/macro` видит живой синтаксис, а поиск (пункт 2) находит их по словам «макрос», «припуск», «границы» |

Если модель не уверена в команде, она обязана оставить комментарий
`// НЕ НАЙДЕНО В ДОКУМЕНТАЦИИ: <что нужно>`, а не выдумывать строку.

### Если батник «закрывается» или сыпет обрывками

Windows запускает `.bat` через `cmd.exe`, который читает файл по байтам. Отсюда
два классических отказа:

| Симптом | Причина | Лечение |
|---|---|---|
| окно закрывается мгновенно, ошибки нет | скобочный блок `( ... )` с русским текстом под `chcp 65001` | переписать плоско: `goto метка` вместо скобок |
| `'ерка' is not recognized`, `'exe" set "PY' is not recognized` | файл сохранён с Unix-переводами строк (LF) — cmd рвёт строки посередине | переводы строк CRLF |

Оба правила теперь закреплены в проекте:

* `.gitattributes` заставляет Git выдавать `*.bat` с CRLF на любой машине;
* `tests/test_bat_files.py` роняет тесты, если в репозиторий попал батник
  с LF, BOM, без `chcp 65001`, со скобочным блоком и русским текстом, с битым
  `goto` или `call`;
* `scripts/repair_bats.bat` (**пункт 26 меню**) сам правит переводы строк
  и печатает отчёт `output\bat_check.txt`;
* `update_from_git.bat` запускает эту починку после каждого обновления.

## Ассистент знает твой проект (шаги 2.0 и 2.1 плана)

Консольный ассистент не видит, что открыто в PowerMill, — поэтому макросы
получались с абстрактными именами. Есть два пути, оба без плагина:

**Живьём (быстрее всего):** PowerMill запущен — ассистент читает проект сам.

```
PowerMill с открытым проектом
start_menu.bat  ->  пункт 24   (читает модели, инструменты, траектории сам)
start_menu.bat  ->  пункт 1    (/project, /macro ... — с твоими именами)
```

**Через макрос** (если PowerMill закрыт):

```
start_menu.bat  ->  пункт 23   (создаёт макрос разведки output\PM_PROBE.mac
                                и кладёт его в папки макросов PowerMill)
PowerMill       ->  лента «Макрос» -> Выполнить -> PM_PROBE.mac
                    (макрос САМ пишет снимок в output\pm_project.txt, сразу
                     читает его обратно и показывает окно: путь, число строк,
                     «Снимок записан» или «ФАЙЛ НЕ ЗАПИСАЛСЯ»)
start_menu.bat  ->  пункт 24   (разбирает этот файл — копировать не нужно)
start_menu.bat  ->  пункт 1    (/macro ... — теперь с твоими именами)
```

Что даёт:

| Команда в чате | Что делает |
|---|---|
| `/project` | показывает объекты проекта и **проверки**: имена-заглушки, дубликаты, траектории без инструментов и NC-программ, отсутствие плоскостей |
| `/macro <задача>` | в подсказке модели теперь настоящие имена (`Rough_D16`, `Blok_40X`) — код оперирует твоими объектами |
| `/ask <вопрос>` | ответы учитывают, что у тебя в проекте |
| `/pm` | пробует живое подключение к запущенному PowerMill (шаг 2.1) |

Макрос разведки использует только надёжные конструкции PML
(`FOREACH ... IN FOLDER("Toolpath") { FILE WRITE $tp.name TO out }`) — никаких
догадок про версии и внутренние переменные. Он **пишет файл**, а не только
печатает в окно сообщений: в PowerMill это окно легко не заметить, и тогда
кажется, что макрос «ничего не делает». Плюс он тут же читает файл обратно и
показывает окно с путём и числом записанных строк — если строк 0, это видно
сразу, а не после разбора пустого файла.

Три вещи, которые макрос делает по опыту живого PowerMill 2026 (каждая — из
конкретной неудачи, а не «на всякий случай»):

| Что | Зачем |
|---|---|
| `RESET LOCALVARS` первой строкой | переменные живут в сессии PowerMill: без сброса **второй** запуск макроса падает на `local variable is already defined` |
| путь только с прямыми слэшами (`E:/powermill-ai/output/pm_project.txt`) | путь с `\` PowerMill не разобрал и вместо файла показал приглашение `Выберите файл >` |
| склейка строк — в `$переменную`, а в `PRINT`/`MESSAGE` — одна переменная | так написаны рабочие макросы Autodesk; что команда принимает выражение с `+`, мы не проверяли |
| в `FILE WRITE`, `PRINT`, `MACRO PAUSE` идёт только **переменная**, не текст в кавычках | `FILE WRITE "WAIT" TO tf1` дал «недопустимый элемент или команда»: во всех рабочих макросах в `FILE WRITE` передаётся переменная |
| файлы макросов — в кодировке **CP1251**, батники — в UTF-8 | PowerMill читает `.mac` в системной кодировке: UTF-8-макрос показывался как «РџРѕРІРµСЂРєР°» (кракозябры), у батников свой `chcp 65001` |
| у каждого шага макроса — свой дескриптор файла и свой файл-отметка | незакрытый файл мешает открыть его снова; по последней отметке `pm_trace_N.txt` видно, на какой команде макрос встал |

**Если в PowerMill появилось `Выберите файл >`** — это PowerMill спрашивает, какой
файл открыть. Бывает в двух случаях: (1) макрос запущен не через ленту, а набором
слова `MACRO` в командной строке — тогда PowerMill спрашивает сам файл макроса,
это не ошибка; (2) в старой копии макроса остался путь с обратными слэшами —
тогда заново запусти **пункт 23**: он пересобирает `PM_PROBE.mac` под этот
компьютер и перезаписывает старые копии.

## Живое подключение и плагин (шаги 2.1 и 2.2)

**`/pm` (шаг 2.1)** пробует три пути по порядку и честно говорит, что вышло:

| Путь | Что нужно | Что даёт |
|---|---|---|
| dotnet | сборка `Autodesk.ProductInterface.PowerMILL.dll` + `pip install pythonnet` | чтение проекта в реальном времени |
| com | COM-регистрация PowerMill + `pip install pywin32` | **работает**: чтение проекта, выполнение команд (проверено на PowerMill 2026) |
| файлы | ничего (работает всегда) | пункты 23–24: макрос + снимок |

Что уже известно про COM-интерфейс PowerMill 2026 (из отчёта разведки, без догадок):

```
Project            — проект (свойства ActiveProject у PowerMill НЕТ)
Models, Tools, Toolpaths, Boundaries, Workplanes, Patterns,
StockModels, NCPrograms, MachineTools, Features, Levels  — коллекции объектов
DoCommand / Execute / DoCommandEx / ExecuteEx           — выполнение команд и макросов
Version, Visible, WindowState, Quit, Exit               — состояние приложения
```

Поэтому ассистент **присоединяется** к запущенному PowerMill
(`GetActiveObject`) и никогда не открывает вторую копию программы сам:

* **пункт 24** — читает проект живьём (модели, инструменты, траектории, границы…)
  и сохраняет снимок `output\project_context.json`; если PowerMill не запущен —
  предлагает снимок макросом, как раньше;
* **`/project`** — обновляет снимок из живого PowerMill и показывает проверки;
* **`/pm`** — пишет версию PowerMill и количество объектов в каждом разделе.

Модуль не угадывает устройство API: он подключается и печатает **настоящие
имена свойств и методов** объекта — по этому отчёту пишется точная интеграция.

**Пункт 25 (шаг 2.2)** готовит плагин PowerMill. Из официальной документации
Autodesk известно, что плагины входят в поставку: в установке есть папка
`file\plugins` с подпапками **Documentation** (как писать плагин на C#),
**Framework** (готовый каркас), **Installers**, **Solutions** (исходники
примеров). Сборка возможна **без Visual Studio**:

```
build.bat      -> csc.exe из .NET Framework (есть в любой Windows)
register.bat   -> regasm.exe PowerMillAI.dll /register /codebase
PowerMill      -> Инструменты -> Плагины (в списке должен появиться наш)
```

Пункт 25 находит каркас, копирует его и примеры к нам в `E:\powermill-ai\plugin`,
вытаскивает из примеров факты о каркасе (классы, интерфейсы, GUID, using) и
пишет отчёт `output\plugin_report.txt`. По этому отчёту пишется код плагина
под конкретную версию PowerMill — а не «в общем виде».

## Кнопка ассистента внутри PowerMill (пункт 28) — уже работает, без плагина

Плагин — это .NET-сборка, regasm и разработка на C#. Но PowerMill умеет всё
нужное **сам**, стандартными командами PML из официального руководства:

| Команда PML | Что делает |
|---|---|
| `FILE OPEN $f FOR WRITE AS h` / `FILE WRITE $t TO h` / `FILE CLOSE h` | макрос пишет текстовый файл |
| `FILE OPEN $f FOR READ AS h` / `FILE READ $lines FROM h` | макрос читает текстовый файл |
| `OLE FILEACTION 'OPEN' <путь>` | макрос запускает внешнюю программу (наш .bat) |
| `INPUT CHOICE`, `INPUT`, `MACRO PAUSE`, `MESSAGE INFO` | меню выбора, ввод строки, пауза с кнопкой RESUME, окно с ответом |

Отсюда мост «PowerMill ↔ ассистент» **через файлы**, без единой сборки:

```
1. В PowerMill запускаешь макрос PM_AI_ASK.mac
2. Он спрашивает: справка / макрос / ошибка / режимы резания, и текст вопроса
   (для режимов резания сразу спрашивает материал и фрезу — см. ниже)
3. Пишет запрос в output\pm_request.txt
4. Сам запускает output\pm_answer.bat  (OLE FILEACTION)
5. Ассистент считает ответ и пишет output\pm_answer.txt
6. В PowerMill жмёшь RESUME — ответ появляется в окне сообщений
```

**Проверено вживую 24.09.2026**: `PM_AI_TEST.mac` показал «МОСТ РАБОТАЕТ
ПОЛНОСТЬЮ», а `PM_AI_ASK.mac` в режиме «Режимы резания» дошёл до конца —
запрос ушёл в файл, батник посчитал ответ, файл `pm_answer.txt` записан, ответ
виден в PowerMill после RESUME. Уровень 2 (2.2) закрыт на живом PowerMill.

Для режимов резания макрос спрашивает материал и фрезу отдельно:

```
Материал (например: сталь 40Х, 12Х18Н10Т, Д16Т):
Фреза: диаметр и число зубьев (например: D12 z4):
```

Это добавили после первого живого запуска: на вопрос «какой фрезой сделать»
ассистент отвечал по «стали среднеуглеродистой» с диаметром по умолчанию и
честно писал «материал не распознан». Если оставить эти поля пустыми, всё
работает как раньше — ассистент примет значения по умолчанию и скажет об этом.

**Первым делом запусти `PM_AI_TEST.mac`** — он за 10 секунд честно проверяет весь

### Если макрос остановился на середине — как узнать, где именно

На живом PowerMill 2026 макрос ведёт себя строго, и «молча остановился» — это
нормальная ситуация, а не загадка. Чтобы не искать виновника по всему файлу,
каждый шаг самопроверки теперь **оставляет свой файл**:

| Файл | Значит |
|---|---|
| `pm_trace_1.txt` | шаг 1 пройден — PowerMill записал файл |
| `pm_trace_2.txt` | шаг 2 пройден — файл прочитан обратно |
| `pm_trace_3.txt` | шаг 3 пройден — команда запуска .bat отправлена |
| `pm_trace_4.txt` | шаг 4 пройден — пауза и RESUME |
| `pm_trace_5.txt` | шаг 5 пройден — внешняя программа ответила (что именно — в файле) |

Правило: **последний по номеру файл = последний сработавший шаг, а следующая
строка макроса — та самая проблемная команда.** Посмотреть файлы: пункт 29 меню.
Кроме файлов макрос печатает короткие строки «powermill ai: шаг N ок» — по ним
видно шаг прямо в окне PowerMill, без открытия файлов.

Второе правило живого PowerMill (проверено 24.09): **в `FILE WRITE`, `PRINT` и
`MACRO PAUSE` уходит только переменная.** Сначала это выяснилось на склейке —
`FILE WRITE "MODE=" + STRING($mode) TO req` остановила макрос; потом на тексте в
кавычках — `FILE WRITE "WAIT" TO tf1` дала «**недопустимый элемент или команда**».
Во всех рабочих макросах с форума Autodesk в `FILE WRITE` передаётся переменная.
Поэтому у нас текст сначала присваивается строке
(`STRING $mode_line = "MODE=" + STRING($mode)`, `STRING $pm_text = "WAIT"`), а в
команду идёт её имя. Проверка автоматическая: `tests/test_pm_macro.py`
(`test_macro_text_never_goes_into_file_write_as_literal`) не даст вернуть ни
склейку, ни литерал.

Третье правило: **кодировка макросов — CP1251.** PowerMill читает `.mac` как
однобайтовый текст в системной кодировке, поэтому UTF-8-макрос в его окне
выглядел как `РџРѕРІРµСЂРєР° РјРѕСЃС‚Р°` — и команды, и русские подписи. Теперь
макросы пишутся в CP1251 (`src/pml_files.py`), там же понятные замены для
символов, которых в CP1251 нет («→» → `->`), а эмодзи убираются. Файл ответа для
окна PowerMill (`pm_answer.txt`) пишется так же; файлы, которые пишет макрос
(запрос, снимок, отчёты `STEP;…`), читаются с автоопределением кодировки —
поэтому и старые файлы, записанные в UTF-8, разбираются по-прежнему.

Если макрос всё же встал: перезапусти PowerMill (незакрытый файл мешает открыть
его снова) и пришли в чат содержимое `pm_trace_*.txt` — по нему видно и шаг, и
содержимое файлов.

Что ещё нашлось в рабочих макросах Autodesk, но **у нас пока не проверено**
(появится в следующих шагах, когда понадобится): `OLE FILEACTION 'open' $переменная`
— путь можно передавать переменной (так делают в макросах, открывающих NC-файлы);
`file_exists($путь)` — похоже, проверка существования файла в PML всё-таки есть;
`WAIT 1` — пауза в секундах (может заменить `MACRO PAUSE` там, где ждать нужно
программу, а не человека). Пока в наших макросах этого нет: сначала проверим
на живом PowerMill.

Запуск всего этого: `start_menu.bat` -> **28** (батник `scripts\prepare_pm_macros.bat`).
Он создаёт макросы, кладёт их в `output\pm_macros` и копирует в папки макросов
PowerMill, если нашёл. Дальше в PowerMill: вкладка **Макрос → Выполнить →
`PM_AI_ASK.mac`**. Кнопку можно закрепить на ленте (правой кнопкой по ленте →
«Настроить ленту» → категория «Макрос»).

| Макрос | Что делает |
|---|---|
| `PM_AI_TEST.mac` | **самопроверка моста** (запускать первым): файлы + запуск .bat + пауза |
| `PM_AI_ASK.mac` | меню режимов, ввод вопроса, показ ответа в PowerMill |
| `PM_AI_SNAPSHOT.mac` | снимок проекта: модели, границы, инструменты, траектории, NC |

Снимок из пункта 28 идёт **без блокнота**: макрос пишет файл сам, а
`output\pm_snapshot.bat` разбирает его (`/project` показывает проверки).

Важно: в макросы попадают **только** команды, которые есть в разобранной
справке или на официальном форуме Autodesk. Проверка автоматическая — тот же
словарь PML (`src/pml_vocab.py`), которым проверяются макросы из `/macro`;
`tests/test_pm_macro.py` не даст протащить выдуманную команду.

Если файла с ответом нет или макрос ругается — запусти **пункт 26** (починка
батников) и посмотри **пункт 19** (логи): мост пишет лог каждого запуска.

## Запись режимов в проект PowerMill (пункт 30, шаг 3.1)

Первый шаг Уровня 3: рассчитанные режимы (S — обороты, F — подача резания,
F врезания) записываются в траектории твоего проекта. Не «в общем виде», а в
конкретные траектории, которые ты назовёшь.

```
start_menu.bat  ->  пункт 30
  1. материал и фреза  (тот же калькулятор, что в пункте 3)
  2. список траекторий (Enter — все, которые видно в проекте)
  3. показать КОМАНДЫ до выполнения
  4. подтверждение (пишешь ДА) + копия проекта «Деталь_AI_дата»
  5. PowerMill запущен -> макрос выполняется сам; закрыт -> запусти его
     из ленты «Макрос» и вернись в пункт 30
  6. отчёт «было → стало»: значения читает обратно сам PowerMill
```

Как это работает внутри (и почему так):

| Что | Команда PML | Откуда взято |
|---|---|---|
| включить страницу подач | `EDIT TPPAGE SWFeedSpeed` | рабочий макрос с форума Autodesk |
| обороты | `$tp.SpindleSpeed.Value = 4500` / `EDIT RPM "4500"` | принятое решение Autodesk Community + тот же макрос |
| подача резания | `$tp.Feedrate.Cutting.Value = 1200` / `EDIT FRATE "1200"` | там же |
| подача врезания | `$tp.Feedrate.Plunging.Value = 400` / `EDIT PRATE "400"` | там же |
| проверка | читаем параметр до и после, пишем строку в `output\pm_edit_result.txt` | наша проверка: отчёт не «на слово», а по факту |

Макрос пробует **параметр траектории**, а если значение не изменилось —
команду `EDIT RPM/FRATE/PRATE`; в отчёте видно, какой способ сработал
(`param` или `command`). Так мы не гадаем: на твоей машине сразу видно, что
работает.

Чего пункт 30 сознательно НЕ делает: не пишет ap/ae (глубины). Команда
известна — `EDIT PAR 'Stepdown'` / `EDIT PAR 'Stepover'` (руководство PowerMill),
но имя параметра зависит от стратегии: для Model Area Clearance понадобилось
`EDIT PAR 'AreaClearance.ZHeights.Stepdown'`. Сначала подтвердим имена на твоих
стратегиях — потом включим и ap/ae. Выдумывать имена = писать «в никуда».

Правила безопасности работают буквально: сначала на экран команды, потом
подтверждение, потом копия проекта (`Деталь_AI_дата`), и только затем правка.
Оригинал проекта не меняется. Отчёт пункта 30 открывается пунктом 29.

## Черновая операция в проекте (пункт 31, шаги 3.2–3.3)

Следующий шаг после записи режимов: ассистент собирает в проекте **рабочую
черновую операцию** — то, с чего начинается любая обработка.

```
start_menu.bat  ->  пункт 31
  1. материал и фреза  ->  режимы (S, F, врезание) считает наш калькулятор
  2. ap/ae             ->  Enter = из расчёта (заглубление и шаг по XY)
  3. ПЛАН и КОМАНДЫ    ->  показываются до выполнения
  4. подтверждение     ->  правка только после «да»; копия проекта — по желанию
  5. PowerMill открыт  ->  макрос уходит в него сам (COM)
  6. отчёт по шагам    ->  что получилось, что PowerMill не принял
```

Что именно делает макрос (и откуда каждая команда):

| Шаг | Команды PML | Источник |
|---|---|---|
| инструмент, если его нет | `EDIT TPPAGE TOOL`, `CREATE TOOL ; <тип>`, `EDIT TOOL ; DIAMETER`, `EDIT TOOL ; NUMBER COMMANDFROMUI`, `RENAME Tool ;` | рабочий макрос Autodesk «Need help altering my macro to create a tool from database» |
| инструмент из проекта | `ACTIVATE TOOL '<имя>'` | форум Autodesk |
| заготовка | `EDIT TPPAGE SWBlock`, `EDIT BLOCK COORDINATE WORLD`, `EDIT BLOCK RESET`, `EDIT BLOCK RESETLIMIT`, `EDIT BLOCK ZMAX` | «Prompting questions in a macro» |
| траектория | `IMPORT TEMPLATE ENTITY TOOLPATH TMPLTSELECTORGUI "3D-Area-Clearance/Model-Area-Clearance.003.ptf"` — это и есть Offset Area Clearance | там же |
| параметры | `EDIT PAR 'CutDirection'/'Tolerance'/'Thickness'/'Stepover'/'AreaClearance.ZHeights.Stepdown'/'ZRange.Minimum.*'` | «Macro not using input» + ответ Autodesk про `AreaClearance.ZHeights.Stepdown` |
| безопасная зона и подводы | `EDIT TOOLPATH SAFEAREA CALCULATE_DIMENSIONS`, `EDIT TOOLPATH LEADS LEADIN RAMP` | «Prompting questions in a macro» |
| проверки | `EDIT PAR 'CollisionCheck' '1'`, `Clearance.Holder`, `Clearance.Shank` | «Macro not using input» |
| режимы | `EDIT TPPAGE SWFeedSpeed`, `EDIT RPM/FRATE/PRATE` | тот же макрос |
| имя и расчёт | `RENAME TOOLPATH ; '<имя>'`, `EDIT TOOLPATH "<имя>" CALCULATE` | «Macro not using input» |

Две честные оговорки:

1. **Тип инструмента.** Документацией подтверждён `CREATE TOOL ; DRILL`; для
   фрезы слова в разных версиях разные. Поэтому макрос пробует `END_MILL`,
   `ENDMILL`, `END MILL` и после каждой попытки проверяет, выросло ли число
   инструментов в проекте. Сработавшее слово попадает в отчёт — дальше будем
   знать точно. Если ни одно не подошло, отчёт скажет об этом прямо.
2. **Расчёт траектории** включается только по твоему «да» — это самая долгая
   операция, и запускать её лучше, когда инструмент и параметры уже проверены
   глазами. Без «да» макрос создаёт операцию, но не считает её.

После запуска смотри в PowerMill: появилась траектория с твоим именем, в её
параметрах — фреза, шаг, заглубление и режимы. Отчёт пункта 31 открывается
пунктом 29 (`pm_operation_report.txt` — что собралось, `pm_operation_result.txt`
— строки `STEP;…` от самого макроса).

## Интерфейс в браузере: чат, прогресс, отчёты (пункт 32)

Двойной клик: `start_menu.bat` -> **32**, либо `scripts\chat_ui.bat`.
Откроется окно браузера (адрес `http://127.0.0.1:8765`) — его можно держать рядом
с PowerMill. Окно консоли, из которого запустился сервер, не закрывать: в нём

| Часть интерфейса | Зачем |

## Фреза в проекте и рабочее слово (пункт 33)

`start_menu.bat` -> **33**, либо `scripts\probe_tool.bat`.

Зачем отдельный пункт, если инструмент умеет создавать пункт 31: **в макросе
неверная команда останавливает весь макрос.** На живом PowerMill 2026 так и
случилось с `FILE WRITE "WAIT" TO tf1` — «недопустимый элемент или команда», и
макрос встал. Если бы так же не повезло со словом фрезы (`CREATE TOOL ; END_MILL`),
мы потеряли бы всю операцию и не узнали, какое слово правильное.

Здесь команды уходят в PowerMill **по одной** через COM, и после каждой
перечитывается список инструментов проекта:

| Что делает пункт 33 | Что видно тебе |
|---|---|
| проверяет, нет ли уже такой фрезы (тогда ничего не создаёт) | «фреза уже есть — создавать не нужно» |
| пробует `CREATE TOOL ; END_MILL`, `ENDMILL`, `END MILL` (проверенное слово — первым) | построчно: какое слово сработало, какое нет и что ответил PowerMill |
| ставит диаметр, номер и имя: `EDIT TOOL ; DIAMETER`, `EDIT TOOL ; NUMBER COMMANDFROMUI`, `RENAME Tool ; 'D16_Freza'` | отчёт `output\pm_tool_report.txt` (открывается пунктом 29) |
| запоминает сработавшее слово в `output\pm_tool_word.txt` | пункт 31 подставит его **первым** и перебирать варианты уже не будет |

Команды показываются **до** выполнения, и только после «да» что-то меняется.
Окна ошибок PowerMill на время проб гасятся (`DIALOGS ERROR OFF` /
`DIALOGS MESSAGE OFF`) и возвращаются как были — иначе неверная команда открыла
бы модальное окно и заблокировала ответ. Если окно всё-таки появилось — нажми в
нём ОК, это не поломка.

Порядок работы: сначала пункт 33 (создать фрезу и узнать слово), потом пункт 31
(черновая операция) — он увидит готовую фрезу и создавать её не станет.

PowerMill.

**Список кнопок — общий с панелью плагина** (пункт 38): он лежит в
`src\pm_buttons.py`, и отсюда же берутся имена макросов-запускателей. Добавил

**Как это сделано (без C# и без плагина).** У PowerMill есть штатные команды
работы с лентой (с форума Autodesk):

```
EDIT CUSTOMRIBBON IMPORT FILEOPEN "<файл.xml>"
EDIT CUSTOMRIBBON APPLY
FORM RIBBON TAB UICATEGORY        // перейти на свою вкладку
```

Настройка ленты лежит в профиле пользователя:
`%LOCALAPPDATA%\Autodesk\PowerMill*\ribbon_customisation.xml`.
Формат этого XML Autodesk **не документирует**, поэтому мы его не выдумываем:
пункт 34 находит в твоём файле уже существующую кнопку с макросом и клонирует
её под наши кнопки, меняя только подписи и путь к макросу. Перед изменением
делается копия файла (`ribbon_customisation_backup_ГГГГММДД_ЧЧММ.xml`) —
откатить можно простым возвратом копии.

Если в настройке ещё нет ни одной кнопки с макросом (лента не настраивалась),
пункт **ничего не меняет** и пишет инструкцию для ручного добавления:

1. `File` -> `Options` -> `Customise the Ribbon and Quick Access Toolbar`;
2. в верхнем списке выбрать **Macro button**;
3. Name: `PowerMill AI`, Picture: любая, Macro -> Open -> макрос из
   `output\pm_macros` (например `PM_AI_CHAT.mac`);
4. **Add>>**, затем переименовать новую вкладку в «PowerMill AI» и нажать OK;
5. пришли файл настройки в чат — после этого автоматический режим заработает.

Отчёт пункта 34: `output\pm_ribbon_report.txt` (открывается пунктом 29). В нём
видно структуру твоего файла ленты, что добавлено и что ответил PowerMill.

## Плагин-панель «PowerMill AI» (пункт 38, шаг 2.3б)

`start_menu.bat` -> **38**, либо `scripts\build_plugin.bat`. Собирает панель
внутри PowerMill: кнопки сценариев и журнал того, что ассистент делает.

### Они объединены, а не существуют отдельно

Три вещи берут кнопки из **одного списка** `src\pm_buttons.py`:

1. **вкладка на ленте** (пункт 34) — кнопка отправляет маленький макрос-запускатель;
2. **панель плагина** (пункт 38) — та же кнопка, но выполняется внутри PowerMill;
3. **сами макросы** (`PM_AI_ASK.mac`, `PM_AI_SNAPSHOT.mac`) — их панель умеет
   запускать напрямую.

Панель плагина делит кнопки на группы:

| Группа | Что в ней | Как выполняется |
|---|---|---|
| **Внутри PowerMill (макросы)** | ассистент-вопрос, снимок проекта | панель находит объект PowerMILL (`PluginServices`, а если не вышло — `Marshal.GetActiveObject`) и отправляет ему `MACRO "<путь>"`; в журнал пишется, какой способ сработал |
| **Сценарии ассистента (отдельное окно)** | режимы, фреза, черновая, проверки, NC, «СДЕЛАЙ», отчёты | открывается отдельное окно — этим сценариям нужен ввод технолога |
| **В браузере** | чат с прогрессом (пункт 32) | вывод идёт в журнал панели |

Мозг в любом случае один и тот же — наш Python: кнопка запускает **тот же
сценарий**, а не второй экземпляр логики. Поэтому ничего не переписывается и
поведение не разъедется.

| Что | Макросы (пункты 28, 34) | Плагин-панель (пункт 38) |
|---|---|---|
| Свои кнопки внутри PowerMill | да, вкладка на ленте | да, панель в списке панелей |
| Список кнопок | общий (`src\pm_buttons.py`) | общий (тот же файл) |
| Выполнение наших макросов | сам PowerMill | сама панель, внутри PowerMill, с журналом |
| Журнал вывода прямо в PowerMill | нет — надо смотреть консоль/отчёты | да, текст идёт в панель |
| Стоимость | уже работает | .NET-сборка + регистрация в COM и реестре |
| Риск | минимальный: просто команды PowerMill | низкий, но системный: правка реестра, DLL |
| Диалоги технолога | полностью работают | сценарий открывается **отдельным окном**, как двойным щелчком |
| Понимание, что выделено/активно | через `$powermill.Status` | то же плюс можно было бы читать выделение напрямую |
| Нужен ли плагин сейчас | — | не обязателен: всё уже доступно через меню и ленту |

То есть плагин — это удобство и «как Copilot внутри PowerMill», а не новая
функциональность. И он, и макросы упираются в одно и то же: команды PowerMill
и проверку результата на станке.

### Как собирается

Visual Studio не нужна:

1. `src\pm_plugin.py` собирает исходник `plugin\PowerMillAI\PowerMillAI.cs` —
   по фактам каркаса Autodesk (класс `: PluginFrameworkWithPanes`,
   `[Guid]`, `[ClassInterface(ClassInterfaceType.None)]`, `[ComVisible(true)]`,
   `register_pane(new PaneDefinition(...))`). UI — WPF (как в примерах Autodesk),
   есть вариант WinForms. **Без XAML:** панель собирается кодом, поэтому хватает
   одного `csc.exe`;
2. `csc.exe` (лежит в .NET Framework) компилирует `PowerMillAI.dll` со ссылкой
   на `Delcam.Plugins.Framework.dll` из поставки PowerMill;
3. `regasm.exe PowerMillAI.dll /register /codebase` — COM-регистрация;
4. запись компонентной категории плагинов PowerMill в реестр (обе ветки,
   `/reg:32` и `/reg:64`) — **без неё PowerMill плагин не подхватывает**. Это
   самая частая причина «собрал, а в PowerMill ничего нет».

Пункт честно проверяет окружение **до** сборки и говорит, чего нет (компилятор,
каркас, Python проекта); реестр трогает только после отдельного «да». Отчёт —
`output\pm_plugin_build_report.txt`, там же команды для отмены регистрации
(`regasm /unregister` + `reg delete`) и инструкция, если панели не видно.

### Что не проверено

* исходник ещё не проходил компилятор — в песочнице csc нет, поэтому если первая
  сборка покажет ошибки, пришли вывод: поправлю (в отчёте это написано прямо);
* что панель появится в PowerMill и что кнопки в ней работают — только вживую;
* какой именно способ вызова PowerMill сработает из плагина
  (`services.PowerMILL` / `DoCommand` / `ExecuteEx` / `Execute`) — панель
  перебирает варианты и пишет в журнал тот, который подошёл; если ни один не
  сработает, она честно скажет и предложит кнопку на ленте;
* что версия каркаса совпадает с установленной версией PowerMill;
* что плагин не мешает другим плагинам (NCSIMUL, ViMill, Robot).

## Проверки, NC и «сказал: делай» (пункты 35–37, шаги 3.4–3.6)

Три шага, которые превращают «ассистент собрал операцию» в «ассистент довёл
работу до программы»:

| Пункт меню | Шаг | Что делает |
|---|---|---|
| **35 Проверить траектории** | 3.4 | запускает штатные проверки PowerMill: зарезы и столкновения, читает статус безопасности траектории |
| **36 Вывести NC** | 3.5 | создаёт NC-программу в проекте, вкладывает траектории, ставит номер и (по желанию) постпроцессор, выводит файл |
| **37 СДЕЛАЙ** | 3.6 | один поток: материал + фреза → план → «ок» → фреза/заготовка/траектория/параметры/режимы/расчёт → проверки → NC → отчёт |

### Проверки (пункт 35)

Проверяет **сам PowerMill**, а мы читаем его результат — так, как это делают в
рабочих макросах Autodesk (тема «Macro to simulate all toolpaths in project»):

```
EDIT COLLISION TYPE GOUGE          // зарезы
EDIT COLLISION APPLY
EDIT COLLISION TYPE COLLISION      // столкновения державки и хвостовика
EDIT COLLISION SHANK_CLEARANCE "0.1"
EDIT COLLISION HOLDER_CLEARANCE "0.1"
EDIT COLLISION SPLIT_TOOLPATH Y
EDIT COLLISION DEPTH Y
EDIT COLLISION ADJUST_TOOL Y
EDIT COLLISION APPLY
```

Результат PowerMill хранит в свойствах траектории, оттуда и читаем:
`$tp.Computed`, `$tp.Verification.GougeChecked`, `$tp.Verification.CollisionChecked`,
`$tp.Safety.Tool.Cutting.Status`. Отчёт (`pm_check_report.txt` + строки `CHK;…`
в `pm_check_result.txt`) показывает и то, что проверено, и то, что **не** проверено
(например, если ты выключил какой-то вид проверок или PowerMill не успел).

### NC-программа (пункт 36)

Собирается командами из рабочих макросов Autodesk («Macro to create NC code»):

```
CREATE NCPROGRAM 'PROGRAM1'
ACTIVATE NCPROGRAM 'PROGRAM1'
EDIT NCPROGRAM ; APPEND TOOLPATH 'Chernovaya_D16'
EDIT NCPROGRAM 'PROGRAM1' FILENAME 'E:/…/PROGRAM1.tap'
EDIT NCPROGRAM 'PROGRAM1' TAPEOPTIONS 'E:/…/станок.pmoptz'
EDIT NCPROGRAM 'PROGRAM1' NUMBER 100
DEACTIVATE NCPROGRAM
ACTIVATE NCPROGRAM 'PROGRAM1' KEEP NCPROGRAM ;     // вывод файла
```

Одноимённую программу в проекте **не затираем молча**: пункт скажет, что такая
уже есть, и попросит подтверждение на замену. В отчёте всегда есть блок
«Что НЕ проверено (честно)»: файл не прогонялся на станке и не проверялся в
NCSIMUL, кадры G-кода мы не сверяем с чертежом, постпроцессор проверяет технолог.

### Две ловушки, на которых эти макросы легко ломаются

1. **Объявления переменных — только на верхнем уровне.** Внутри `IF/ELSE`
   PowerMill допускает лишь присваивание; повторное `STRING $x = …` в блоке
   даёт «local variable is already defined» (мы на этом уже спотыкались, когда
   стали делать проверки для нескольких траекторий). Поэтому макросы пунктов
   35–37 сначала объявляют все переменные, а внутри блоков только присваивают.
   Тесты это стерегут: `test_macro_declares_each_variable_once`.
2. **`KEEP NCPROGRAM` может задать вопрос.** В рабочих макросах Autodesk сразу
   за `ACTIVATE NCPROGRAM … KEEP NCPROGRAM ;` идёт строка `YES` — это ответ на
   подтверждение (в том числе при перезаписи файла). Поэтому макрос пункта 36
   тоже отвечает `YES`, а строку «файл выведен» пишет **после** вывода. Но
   главное доказательство — не строка в отчёте, а **сам файл**: сценарий читает
   `project_pathname(0)`, ищет свежий файл в `<проект>\ncprograms` (или по
   указанному пути) и пишет размер. Нет файла — так и скажет, а не «наверное,
   вывелось».

### «Сказал: делай» (пункт 37)

Один сценарий вместо пяти пунктов: ты задаёшь материал, фрезу и припуски —
ассистент показывает **план с числами** (диаметр, шаг, заглубление, S/F, лимиты,
что проверяется) и спрашивает «поехали?». Дальше по шагам:

1. копия проекта (если указал папку);
2. фреза — создаётся или берётся из проекта;
3. заготовка по модели с припусками;
4. траектория из шаблона + параметры + режимы;
5. расчёт (если разрешил);
6. проверки зарезов и столкновений (пункт 35);
7. NC-программа (если попросил);
8. отчёт `pm_flow_report.txt`: что сделано ✔, где ✘, что не проверено, на что
   посмотреть.

Поток останавливается на первом же шаге, который PowerMill не принял, и **пишет
об этом прямым текстом** — чтобы не было «вроде что-то создалось». Если нет
модели в проекте, нет живого PowerMill или фрезы нет в проекте, а ты просил
взять готовую — пункт скажет это до запуска.

Что ассистент по-прежнему не делает: не понимает чертёж и допуски, не выбирает
стратегию «по ощущениям» вместо правил и не заменяет пробный прогон на станке.

### Уровень 3 — «сказал: делай» (в работе, по шагам)

Короткий ответ: **да, к этому и идём** — «деталь + материал + фреза → ассистент
сам собрал операции». Но не одним прыжком: команды создания траекторий нельзя
выдумывать, их берём из справки (словарь PML) и проверяем на твоём PowerMill
через живой COM. Поэтому шаги такие:

| Шаг | Что делает ассистент | Что видно тебе | Чем рискуем |
|---|---|---|---|
| **3.1 Запись режимов** ✅ | вписывает S, F и F врезания в траектории проекта (пункт 30) | команды показываются **до** выполнения, отчёт «было → стало» | ничем: правится руками |
| **3.2 Условия резания** ✅ | фреза в проекте (пункт 33 — с выяснением рабочего слова), заготовка (Block) по модели, ограничения по Z (пункт 31) | список созданного по шагам | низкий |
| **3.3 Траектории** ✅ | создаёт траекторию из шаблона стратегии, ставит параметры и режимы, расчёт — по отдельному подтверждению (пункт 31) | план операций списком + отчёт по шагам | средний: считается траектория, металл не режется |
| **3.4 Проверки** ✅ | зарезы и столкновения штатными командами PowerMill + чтение статуса безопасности траектории (пункт 35) | отчёт проверок файлом: что проверено, что нет | нет |
| **3.5 NC-программы** ✅ | создаёт NC-программу, вкладывает траектории, ставит номер и постпроцессор, выводит файл (пункт 36) | NC-файл + честный список «что не проверено» | средний |
| **3.6 «Делай»** ✅ | материал + фреза → **план с числами** → «ок» → выполнение по шагам (фреза, заготовка, траектория, параметры, режимы, расчёт) → проверки → NC (пункт 37) | план до старта, отчёт после | управляемый |

Правила безопасности — в коде, а не на словах:

1. Ассистент **не меняет проект молча**: сначала показывает команду текстом,
   выполняет — потом показывает, что стало.
2. Работаем на копии проекта (`Деталь_AI.pmlprj`), оригинал не трогаем.
3. После каждого расчёта — проверки; «готово» печатается только вместе со
   списком того, что проверено, а что нет.
4. Стратегию ассистент выбирает **по правилам из файла конфигурации и по твоим
   шаблонам**, а не «по ощущениям» — правила можно править и обсуждать.
5. Чего не может (поставить продукты Autodesk, гарантировать безопасность
   режимов на твоём станке) — говорит прямо, а не делает вид.

Что ИИ реально может сам: распознать по геометрии типовые элементы (отверстия,
карманы, стенки, радиусы), предложить набор стратегий и порядок, посчитать
режимы, собрать шаблон операций, выполнить его и проверить результат.

Чего не может: понять чертёж и допуски, если их нет в модели или текстом, и
заменить технолога в спорных местах. Поэтому первый режим — «предложил план →
ты поправил → выполнил», а **проверка после** — не формальность, а часть
сценария (шаги 3.4–3.5 для этого и сделаны, пункт 37 собирает всё вместе).

Дальше по этому уровню (позже): чтение PDF-каталогов и видео (папки
`data\pdf`, `data\videos` готовы), обучение на твоих проектах («в прошлый раз
для такой детали делал так»), разбор STEP/STL для распознавания элементов.
